# 🛠 Xray Config UI Editor: Development Guide

This guide describes the project-specific conventions and technical stack for the Xray Config UI Editor.

## 🚀 Quick Start
- **Runtime**: Bun (use `bun install`, `bun run dev`, `bun run build`)
- **Main Stack**: React 19 + Vite 7 + Tailwind CSS 4 + TypeScript.
- **State**: Zustand 5 + Immer (central store at `src/store/configStore.ts`).

## 📦 Architecture & Logic
- **Configuration Schema**: The source of truth is hand-authored Zod, in `src/core/xray/schemas/**`. `src/utils/config.schema.json` is auto-generated (`bun run schema:generate`, from Xray-core's Go sources) and only backs the raw-JSON editor's Ajv linter — the two can drift; see `ROADMAP.md` item C before assuming they agree.
- **Validation**: `src/core/validators/index.ts` (Zod-based) and `src/core/diagnostics/index.ts` (`runFullDiagnostics`, semantic checks). `saveToRemnawave()`/`saveActiveProfile()` in `configStore.ts` gate on `runFullDiagnostics` critical findings.
- **Store Actions**: Use `useConfigStore` and its actions (`updateSection`, `addItem`, `updateItem`, `saveToRemnawave`) for any state changes.
- **Snippets**: Remnawave config profiles may carry `{ "snippet": "NAME" }` placeholders inside `routing.rules` / `outbounds`; the panel expands them before a node sees the config. `src/core/snippets` is the single source of truth for detecting, validating and (preview-only) expanding them — any new code that iterates rules or outbounds must skip references via `isSnippetRef` instead of linting them, and must never rewrite one in place (that silently unlinks the profile from the panel's central copy). The same module backs the local "templates" library in `configStore.snippetLibrary`.
- **Config generators**: `src/core/generators/local-balancer.ts` builds whole *client* configs (local inbounds + balancer + probe + bypass) from a list of nodes. It is pure — no store, no clock, no randomness — so it is unit-tested directly; keep it that way and put UI state in `src/hooks/useLocalBalancerBuilder.ts` instead. The five things that must agree in such a config (tag prefix, balancer selector, probe subjectSelector, catch-all rule's balancerTag, bypass list duplicated into DNS) are derived there — don't reintroduce them as separate inputs.
- **Panel-derived client outbounds**: `src/core/generators/client-outbound.ts` mirrors a Remnawave *host* + the inbound it references into a client outbound, deriving the REALITY public key from the inbound's private key. Its counterpart is `buildLocalBalancerTemplate()`, which emits an `XRAY_JSON` subscription template carrying `remnawave.injectHosts` instead of inline proxies — that is how a panel hands one balanced config to every subscriber. Both are pure; the panel round-trip lives in the store (`fetchPanelCatalog`, `fetchSubscriptionTemplates`, `saveSubscriptionTemplate`), whose state is deliberately session-only.
- **Reading a balancer back**: `parseLocalBalancer()` (same module as the builders) turns a template or client config into the options that would rebuild it, and reports in `notes` whatever it could not represent. Keep it symmetric with the builders — the round-trip tests in `local-balancer.test.ts` are what stop the two from drifting.
- **Modals on mobile**: a two-column modal must show one pane at a time below `md` — with both mounted the second column collapses to zero height and everything in it, including its buttons, becomes unreachable. `RoutingModal` (mobileEditMode), `LocalBalancerModal` (mobilePane), `SnippetsModal` and `TemplatesModal` (draft presence) all do this; copy one of them rather than inventing a third layout.
- **Defaults and curated lists** live in `src/core/presets/**`, never inline at a call site: `dns.ts` (resolvers, default upstream, `createDefaultDns()`) and `bypass-domains.ts` (`BYPASS_LISTS` plus the split/compose helpers the builder round-trips through). If you need `1.1.1.1` or a domain list in new code, import it from there — the point of the module is that there is one copy to change.
- **Writing to someone's panel**: build the request from a diff, never from the whole object. `src/core/generators/host-payload.ts` is the pattern — `buildHostPatch(draft, original)` returns only changed fields (and `null` for cleared optional ones), so panel settings this app does not model are left alone. Anything new that PATCHes a panel resource should do the same.
- **One object, one screen**: a panel template is edited inside `LocalBalancerModal` (form ↔ JSON), not in a separate modal — if you are about to add a second editor for something this app already writes, add a view to the existing one instead. The module row in `ConfigDashboard` is split into Core (edits the open config) and Remnawave (reads/writes the panel); put new entry points in the group that matches what they touch.
- **Core versions**: a config is only right or wrong relative to the core that loads it, so every "does this field exist / is this value allowed" question is asked of a version. `src/core/xray/versions/` holds the supported lines (`index.ts`: 26.3 = v26.3.27, the floor; 26.7 = v26.7.28, what Remnawave nodes run and the default; 26.9 = v26.9.9, the last release before MASQUE and xdrive; 26.9.30 = v26.9.30, the previous release and a line of its own; 26.10 = v26.10.10, the newest) and what each does with a key or value: `accepted`, `deprecated`, `absent` (the struct has no such field — Go's decoder drops it silently) or `rejected` (Build() errors, the config does not load). Rows come from `features.data.ts` (generated by `scripts/core-versions/build-features.ts` from `scripts/core-versions/findings/*.json`), hand-written rows in `features.ts` and `features.<area>.ts` (`features.masque.ts` and `features.v2610.ts` hold what v26.9.30 and 26.10 added), value sets per line (`VALUE_SETS`), and combination rules in `rules.ts`. Every per-line table has a column for every line, written with `byLine(v263, v267, v269)` (`versions/by-line.ts`; the row helpers `s`, `everywhere` and `same` are thin wrappers): with three values 26.9.30 and 26.10 follow 26.9, so a row that v26.9.30 and v26.10.10 both left alone needs no edit. A row whose 26.9 and 26.10 values differ has no such form — the signature has no four-value overload, so it is `byLine(v263, v267, v269, v2693, v2610)`, stating both, and it cites `v26.9.30:file:line` and `v26.10.10:file:line` (`features.v2693.test.ts` and `features.v2610.test.ts` fail otherwise). Do not guess the 26.9.30 value from its neighbours: it matches 26.9 for `dns.script`, `routing.script`, the dns server `id`, `tlsSettings.useSystemCA` and `masqueSettings.warp`, matches 26.10 for MASQUE, xdrive, the tun keys, noise `exp`, Shadowsocks and the finalmask chain, and matches neither for xdns. Every finding in `findings/*.json` carries its own status and `v26.9.30:` citations, and `build-features.ts` skips one that lacks a status for any line. A key inside an object a line does not know carries `coveredBy` (the id of the object's own row) so a config holding the whole object gets one diagnostic, not one per key. `check.ts` turns them into diagnostics — `rejected` is critical and blocks saving to the panel. Editors ask through `useCoreVersion()` (`offersAt`, `statusAt`, `values`): offer only what the chosen line accepts, and show — never silently drop — a value a config already has, labelled with its status. Every fact cites `tag:file:line`; read the tag's source, not `main`. A line's tag moves to a later patch only when that patch changed nothing a config can say; when one did, it gets a line of its own, named by the patch it starts at (`26.9.30`), and `coreVersionId()` reads a stored 26.9.x tag to the right one (patch 30 and later is `26.9.30`, anything below stays `26.9`). v26.9.30 is that: it registers the `masque` protocol and transport and the `xdrive` transport, adds the two tun keys and the noise `exp` item, runs Shadowsocks 2022 on the core's own package (names lower-cased, keys exactly N bytes) and finalmask without chain levels, hands xdns objects (`name`, and `{type, settings}` resolvers, with record `types` required), and loses WireGuard's `domainStrategy`, `remoteDNS: ["local"]` and udphop's `sockopt`. It has none of what 26.10 added on top: `masqueSettings.warp` (WARP over MASQUE is 26.10-only, so the generator's MASQUE switch stays off there), `useSystemCA`, the dns and routing scripts, the dns server `id`, and xdns's `names`/`addrs`. `git diff v26.9.30 v26.10.10` is empty for most of what the two share (`infra/conf/{shadowsocks,wireguard,tun,masque,xray,loader}.go`, `proxy/shadowsocks_2022`, `proxy/wireguard/client.go`, `proxy/masque`, `transport/internet/{finalmask except xdns,xdrive}`), so a line number there holds in both tags; check that first when deriving a 26.9.30 fact, and cite `v26.9.30:` where it differs. Adding a line: fetch the tag, run `scripts/core-versions/inventory.ts <repo> <outDir>` (per-tag struct JSON and a key-level diff between neighbours; the outputs are not committed), re-derive the findings with the new column (a finding whose cited lines the diff did not touch only needs the new tag's line number; everything the diff touched is read again), add it to `CORE_VERSIONS` and to `TAG_TO_ID` in `build-features.ts`, rerun the generator, then walk every hard-coded `compareCoreVersions(..., '26.x')` and `Record<CoreVersionId, …>`: an index comparison treats a new line between two others as the earlier one for `<` and the later one for `>=`, which is right only if the source says so.
- **Offered is not shown**: two questions that look like one. *Offered* — may the form let someone add this? — is answered by the chosen core line and by `src/core/xray/outbound-shape.ts`. *Shown* — is this in the config already? — is answered by the config, and the answer is always "then draw it". `OutboundModal` keeps them apart (`show.mux = shape.mux || local.mux !== undefined`), because a value the form will not draw is still in the JSON, still built and validated by the core, and now invisible. Removing a control needs the tag's source to say every supported line refuses or ignores the field; "the development branch removed it" is how the proxy-chain chooser went missing for six releases (1.22.0 → 1.27.0) while two of the three supported lines ran it.
- **Outbound chaining**: `src/core/xray/outbound-chain.ts`. An outbound goes out through another one in two ways that are different code in the core, not two spellings: **L4** is `streamSettings.sockopt.dialerProxy` (the outbound dials normally, the socket underneath comes from the other one; every line has it), **L7** is `proxySettings.tag` (the other outbound carries the stream and only TLS of this one's stream settings is applied; 26.3 and 26.7 run it, 26.9 refuses any `proxySettings`). `proxySettings.transportLayer: true` is the old way to ask for L4 — the loader rewrites it to `dialerProxy`. Both keys at once is a load error, so `withChain` always clears the one it is not setting. The card is `outbound/OutboundChain.tsx`; the dashboard badge and the "unreachable" verdict read the same module through `core/routing/outbound-routing.ts`, where an exit that only carries another outbound's connections counts as reached.
- **A field is the type the core decodes**: a key the core's struct reads as an object must never be bound to a text input — a string there fails the decode of the whole document, not just that key. `SchemaForm` draws only what it can type correctly; anything else gets a dedicated editor through its `fieldEditors` prop (`shared/TransportSettings.tsx` — `FallbackLimitEditor` for REALITY's limits, `SockoptEditor` for `echSockopt`), or `ui/JsonInput` when free-form JSON is the honest shape. A value already of the wrong type is shown by `ui/WrongTypeNotice` with a way to clear it, never coerced. The words for TLS/REALITY live in `src/core/xray/security-fields.ts`, shared by the fields and by `securityFieldRules` in `versions/rules.ts`.
- **Rules a form and the diagnostics both state** live in one core module, and both read it: `wireguard-inbound.ts` (`wireguardInboundProblems`, per-line), `freedom-fragment.ts` (`fragmentProblems`, `noiseProblem`), `outbound-credentials.ts` (which of the two shapes a socks/http outbound keeps its login in — `settings.user` beside a flat `address`, else `servers[0].users[0]`; `withCredentials` writes back to the shape it found), `masque.ts` (`masqueProblems`: MASQUE needs the masque transport and TLS, refuses Mux, and the transport belongs to the masque proxy alone; `masqueSettingsProblems` states what `MasqueConfig.Build()` refuses — path variables, host, headers, and the `warp` identity, whose keys `warp-keys.ts` reads as Go's x509 does: PEM or base64, PKCS #8 or SEC 1 on ECDSA P-256, PKIX), `wireguard-config.ts` (what a WireGuard inbound and outbound judge alike) with `wireguard-outbound.ts` beside the inbound module, `shadowsocks-rules.ts` (what both ends share: per-line method matching and 2022 key rules) with `shadowsocks-inbound.ts` and `shadowsocks-outbound.ts`, `tun-outbounds-interface.ts`, `routing-webhook.ts`, `routing-attrs.ts`, `http-outbound-headers.ts` (all three map[string]string in the core: a `null` value decodes to "" and loads, a number does not — `string-map.ts`), `xdrive.ts`. A `z.record(z.string(), z.string())` is drawn by SchemaForm as a `string-map` JSON box, which refuses non-string values. A check that exists only in a component is a check the panel save never runs. Before adding one, look for a value set in `versions/features*.ts` that already reports it — `settings.noises[].type` is one, which is why the diagnostics only add the *missing* type.
- **Noise (decoy datagrams)**: `src/core/noise/` builds the packets a finalmask `noise` layer sends ahead of real traffic. A config can only hold bytes, so the editable form is a *recipe* (`recipe.ts`): a list of steps, each either a `Template` (sip / quic / dns / stun / raw hex / an AmneziaWG tag chain) plus the seed it was drawn with, or a junk step. `renderStep` is a pure function of (template, seed), which is what lets a parameter edit rebuild one field without reshuffling every other packet — pressing the dice is `redrawTemplate`, which redraws the incidental identity and keeps the choices (a SIP method, a QUIC SNI). Recipes live in the editor session only; `toNoiseItems` is the only thing the config ever sees, and reading a layer back gives `hex` templates because the parameters were never stored.
  - Packet builders are in `packets/` and are all `async (params, rng) => Uint8Array`, each citing the RFC for every wire-format decision. The QUIC Initial is a real one — RFC 9001 header protection and AEAD through WebCrypto — and `quic.test.ts` pins it against the RFC 9001 Appendix A vector, so do not "simplify" it without re-running that.
  - `awg.ts` maps to and from AmneziaWG. Its job is mostly honesty: `I1..I5` and `Jc/Jmin/Jmax` carry across, while `S1..S4` (padding on WireGuard's own messages) and `H1..H4` (its message type numbers) change the protocol itself and cannot — a profile with non-default `H` describes a peer this app cannot reach, which is a `critical` note, not a silent drop. `S1/S2` are **not** `settings.reserved`; that is Cloudflare WARP's three-byte header substitution, and the importer used to conflate them.
  - Fixed packets in `src/core/presets/noise.ts` are generated by `scripts/build-noise-presets.ts` — regenerate rather than hand-editing the hex.
- **WARP registration**: the editor never calls `api.cloudflareclient.com` itself — a page cannot (no CORS, no client User-Agent). It goes through the relay Worker in `workers/warp`, deployed as `xcui` (`bunx wrangler deploy` from that folder). The browser makes every key pair (X25519 for WireGuard, ECDSA P-256 through WebCrypto for MASQUE, `core/generators/masque-keys.ts`) and sends only public keys; the relay forwards `POST reg` and `GET`/`PATCH reg/:id` with the Android client's header set, validates every field, and answers only callers sending `X-Xcui-Key`. The built-in key lives in two places that must match — `BUILT_IN_KEYS` in `workers/warp/src/index.ts` and `BUILT_IN_RELAY` in `src/core/generators/warp-relay.ts`; it ships in a public bundle, so it stops drive-by use and is not a secret. Settings → WARP Worker URL and key point at someone's own copy. Cloudflare rate-limits registrations from Workers egress (429, error 1015) for about a minute at a time, which is why the WireGuard generator still adds a keyless profile when registration fails. A change to the relay's contract ships as worker deploy + editor release together: the published editor talks to whatever is deployed. The generators are `warp.ts` (WireGuard) and `warp-masque.ts` (MASQUE, 26.10+); unit tests cannot tell whether a core actually connects, so after changing either, re-run the live check — the relay under `wrangler dev --remote`, a released Xray binary, and `cdn-cgi/trace` through it showing `warp=on`.
- **Topology**: Traffic flow visualization is managed by `@xyflow/react` (React Flow) in `src/components/topology/`.
- **UI/store boundary**: `src/components/ui/**` must never import `useConfigStore` — enforced by an ESLint rule (`eslint.config.js`), not just convention. Editors bind fields via `useField`/`useArrayField` (`src/hooks/useField.ts`) instead of hand-rolled `onChange(path, value)` wiring; see `src/components/editors/inbound/InboundClients.tsx` as the reference example.

## 🎨 UI Guidelines
- **Modals**: All editing forms live in `src/components/editors/`.
- **Styling**: Tailwind 4, compiled at build time via `@tailwindcss/vite` (`vite.config.ts` + `src/index.css`) — not a runtime CDN script. Custom component classes (`input-base`, `label-xs`, ...) live in `src/index.css`.
- **Icons**: Use `@phosphor-icons/react` for consistency.

## 🔖 Releases & Changelog
- **Version format**: `v{TAG}-{GIT-HASH}` (e.g. `v1.0.0-a1b2c3d`), dynamically embedded into the app header/about modal.
- **Tag-based deployment**: Pushing a version tag (e.g. `git tag -a v1.0.0 -m "Release v1.0.0"` and `git push origin v1.0.0`) automatically triggers GitHub Actions to:
  1. Build & deploy the website to GitHub Pages.
  2. Create a clean GitHub Release (without attaching binary asset files).
- **Changelog**: All user-facing features and fixes must be recorded in `changelog.md` starting from `[1.0.0]`.

## 💡 Best Practices
1. **State updates — NOT always `produce`**: Most config-mutating actions in `configStore.ts` (`updateSection`, `addItem`, `updateItem`, `deleteItem`, `moveItem`, `reorderRules`, ...) deliberately do NOT use immer's `produce`. They go through `resolveMutableConfig()`, which parses `rawConfigText` via `parseJsonc` (preserving user comments) and mutates that plain object directly. **This is load-bearing, not incidental** — `immer.produce()` silently strips `comment-json`'s comment metadata on any nested mutation, even on a correctly-parsed object (verified empirically, see `src/utils/jsonc.test.ts` and commit `6a7a0f8`). Simple top-level state replacements (`state.config = newConfig`, `state.remnawave.token = ...`) still use `produce` safely — the danger is only in deep-mutating an already-comment-parsed config object. See `ROADMAP.md` before touching this.
2. **Type Safety**: Ensure all new config parts match the TypeScript interfaces in `configStore.ts`.
3. **No Backend**: Remember, this is a **static** web app; all logic must be browser-compatible.
4. **NO BINARIES**: Never commit images, screenshots, or any binary files. Use `.gitignore` and keep UI documentation external.
5. **Verify every change** with: `bunx tsc --noEmit -p tsconfig.json`, `bun run lint`, `bun test`, `bun run build`. All four are clean on `main` — **tsc reports zero errors**, so expect zero rather than comparing counts. (This line used to claim a baseline of ~80 pre-existing errors; that has not been true for some time, and measuring against a phantom baseline hides real errors.) `bun test` also enforces two generated files: run `bun run icons:generate` after using a new Phosphor icon name (the generator scans every `.ts`/`.tsx` under `src/`, test files included, for quoted words that are icon names — a `'clipboard'` literal in a test stub changes the map just as a real icon does), and keep `src/i18n/ru.ts` in step — `bun run i18n:report` lists what is missing or stale.
